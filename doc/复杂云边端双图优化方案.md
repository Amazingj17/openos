# TriSched 复杂云—边—端双图优化方案

## 1. 一句话介绍

新版 TriSched 不再只处理“任务只有 workload、资源只有 speed”的小型理想场景，而是在赛题限定的端、边、云三类资源内，引入 CPU 核数、内存、GPU/能力约束、任务—资源亲和性和真实网络拓扑，并让强化学习同时理解“任务之间的依赖图”和“资源之间的通信图”。

它解决的仍是同一个赛题问题：每一步从所有合法的 `(就绪任务, 兼容资源)` 中选一个动作，使整个 DAG 的 makespan 尽量小。

## 2. 必须先讲清楚的执行流程

```text
Scenario（任务图、资源图、异构参数）
                  ↓
Env 计算当前 ready tasks、资源兼容性、最早可插入时间
                  ↓
得到当前合法动作集合：(任务2,端)、(任务2,边1)、(任务5,云2)…
                  ↓
双图 Actor 为这些“单步候选动作”打分并选择一个
                  ↓
Env 把该任务插入相应资源时间线的最早空隙，状态发生变化
                  ↓
重复，直到所有任务都被调度，最终形成完整调度方案
```

因此：

- `env.py` 输出的是当前一步的合法键值对集合，不会一次生成完整任务队列；
- TaskGNN 或双图 GNN 也不会先枚举所有完整队列，它只给当前合法动作打分；
- 完整方案是 Actor 和 Env 多轮交互后逐步形成的；
- “寻找资源时间线最早空隙”在 `env.py` 的 `earliest_slot()` 中实现，属于环境动力学，不属于 GNN；
- Actor 负责选动作，Critic 估计状态价值，GAE 根据整段轨迹计算优势，PPO 使用优势更新 Actor 和 Critic。四者合在一起才是完整强化学习方案。

## 3. 场景模型 V2

对应代码：`trisched/scenario.py`。

### 3.1 任务属性

| 字段 | 含义 | 对调度的作用 |
|---|---|---|
| `workload` | 基础计算量 | 影响执行时间 |
| `cpu_cores_required` | 所需 CPU 核数 | 核数不足的资源直接被 mask |
| `memory_required` | 所需内存 | 容量不足的资源直接被 mask |
| `accelerator_required` | 是否必须有 GPU/加速器 | 无加速器资源不能执行 |
| `required_features` | 例如 gpu、trusted_local | 缺少能力标签的资源不能执行 |
| `task_type` | cpu/data/gpu/generic | 用于表达资源亲和性并进入图特征 |

任务边的 `data` 表示父任务向子任务传输的数据量，不再只表示“有依赖”。

### 3.2 资源属性

| 字段 | 含义 |
|---|---|
| `kind` | 只能是 device、edge、cloud，严格对齐赛题 |
| `speed` | 基础处理速度 |
| `cpu_cores` | 可提供的 CPU 核数 |
| `memory_capacity` | 内存容量 |
| `has_accelerator` | 是否有 GPU/专用加速器 |
| `features` | 资源能力标签 |

资源仍是单任务时间线模型：同一资源不能同时运行两个任务。CPU 核数在当前版本中是“任务能否放上去”的硬约束，而不是多任务同时分配核数的连续资源模型。这一边界需要在答辩中如实说明。

### 3.3 非一致异构执行时间

旧模型固定使用 `workload / speed`，意味着云节点对所有任务都按同一比例更快。V2 可配置 `execution_times[task_id][resource_id]`：GPU 任务在云 GPU 上可能极快，数据任务可能在边缘节点更有优势，设备上的本地任务可能避免传输后反而更快。

这使问题从简单的“相关机器”调度升级为更真实的“无关异构机器 + 通信 + DAG 约束”调度。

## 4. 环境和合法动作

对应代码：`trisched/env.py`。

当前动作集合为：

```text
ready_tasks × compatible_resources(task)
```

兼容性同时检查核数、内存、加速器和能力标签。训练与推理都调用同一个 `candidate_actions()`，所以不会出现训练时允许、推理时禁止的行为差异。

当 Actor 选中 `(task_id, resource_id)` 后，`earliest_slot()` 会计算：

1. 所有前驱完成并把数据传到该资源的最早时刻；
2. 该资源已有执行区间之间能否容纳当前任务；
3. 找到第一个可用空隙，而不是一律追加到队尾；
4. 返回 earliest start 和 earliest finish。

## 5. 双图 Actor

对应代码：`trisched/dual_graph.py`。

### 5.1 任务图

一个任务是一个节点。节点包含 workload、upward rank、入度、出度、内存、核数、加速器要求和任务类型。父子边的权重包含数据量，消息分别沿前驱和后继方向聚合。

与原 TaskGNN 相比，V2 不只是知道“谁依赖谁”，还区分大数据依赖和小数据依赖。

### 5.2 资源图

一个具体资源实例是一个节点，例如 device-0、edge-0、edge-1、cloud-0。节点包含速度、核数、内存、加速器、资源层级、当前 ready time 和已分配任务比例。

资源之间的边由 `bandwidth / (1 + latency)` 构造并归一化。于是模型能够区分：

- 两个速度相同但网络位置不同的资源；
- 计算快但远、通信代价高的云节点；
- 计算稍慢但靠近数据来源的边缘节点；
- 当前空闲和已经积压很多任务的资源。

### 5.3 候选动作融合

每个合法 `(任务, 资源)` 同时取得三类信息：候选对特征、该任务的图上下文、该资源的图上下文。三者融合后输出一个 score，对当前合法集合做 softmax 得到概率。

资源节点放进图的收益是能显式感知通信拓扑、资源数量可变和邻居关系；代价是参数和计算量增加，资源图定义不合理时也可能引入噪声。因此仓库保留原 TaskGNN，便于做 `MLP / TaskGNN / DualGraph` 消融实验，而不是直接删除旧方案。

## 6. 强化学习各模块的分工

| 模块 | 输入 | 输出 | 是否直接选动作 |
|---|---|---|---|
| Actor（双图网络） | 当前状态和合法动作 | 每个合法动作的概率 | 是 |
| Critic | 当前合法候选的 mean/max 汇总 | 当前状态的期望累计收益 | 否 |
| GAE | reward、Critic value、后续轨迹 | 每一步 advantage | 否 |
| clipped PPO | 新旧动作概率、advantage | 稳定的参数更新 | 否 |

Actor 是执行调度决策的策略网络，但只有 Actor 不能称为完整 PPO 强化学习。训练时 Actor、Critic、GAE、PPO 和环境奖励共同构成 DRL；推理时只需要 Actor 和 Env。

V2 reward 仍采用每一步 makespan 增量相对于 HEFT makespan 的负值。`gamma=1` 时，一条轨迹的 reward 总和严格等于 `-RL_makespan / HEFT_makespan`，与赛题主指标方向一致。

训练不是从随机策略盲目探索：先使用训练集上的合法 HEFT 轨迹做行为克隆预热，再执行 PPO。每个 PPO epoch 后只在 validation 上比较；若 PPO 退化，则保留 BC 或更早 epoch 的 Actor。该回退只防止训练退化，不保证模型一定优于 HEFT。

## 7. 数据入口

对应代码：`trisched/data_sources.py`。

### STG / GrapheonRL benchmark

`load_stg_json_v2()` 保留 `cores`、`memory_required` 和 `features`，再映射到多实例端/边/云资源。旧 `load_stg_json()` 保持不变，以免破坏已经发布的 v1 manifest 和 hash。

### DAGBench

`load_dagbench_json()` 读取官方说明中的 SAGA-compatible `graph.json`：任务 `cost`、依赖 `size`、网络节点 `speed`、网络边 `speed`。DAGBench覆盖从 1 个任务到 1000+ 任务的多领域 DAG，适合进行规模、结构和领域 OOD 划分。

### Topology Zoo

`load_topology_zoo_graphml()` 读取安全、可移植的 GraphML。稀疏网络通过最宽路径得到端到端有效带宽，通过最短路径得到端到端时延。`scenario_with_topology()` 可以把同一任务 DAG 放到不同资源网络上，专门测试网络泛化。

某些第三方 Topology Zoo 派生仓库使用 Python pickle。项目不直接反序列化不可信 pickle，建议先离线转换为 GraphML；计算层级的映射属于实验假设，当前默认按节点名和度数确定，正式实验应冻结映射清单。

Zenodo 20419279 是结果数据而非新的训练工作流，而且权利信息需要单独核验，不应直接并入训练集。

## 8. 一键运行与输出

```powershell
python -m trisched train-dual-graph --config configs/complex_dual_graph.json
```

默认配置是快速工程 smoke，实测可以在数秒级完成，但不代表正式性能。默认输出目录 `outputs/complex-dual-graph/`：

```text
actor.npz                       双图 Actor checkpoint
critic.npz                      Critic checkpoint
training_curve.json             每个 epoch 的训练记录
validation_per_instance.csv     同场景、同 HEFT 参考的逐实例结果
summary.json                    mean ratio、方差、样本数和模型说明
```

## 9. 推荐实验设计

1. ID：相同生成规则，不同 seed，任务数 40–80。
2. Size-OOD：只改变任务数到 100–300，其他因素尽量固定。
3. DAG-OOD：训练使用合成图，测试使用未参与训练的 DAGBench family。
4. Network-OOD：同一批 DAG 更换 Topology Zoo 网络图。
5. Constraint-OOD：提高 GPU、内存和核数需求，但保证每个任务至少有一个合法资源。
6. 消融：HEFT、CPOP、Greedy-EFT、MLP-PPO、TaskGNN-PPO、DualGraph-PPO。
7. 统计：报告样本数、mean/std、P50/P95、胜平负和配对 bootstrap CI。

不要把一次小规模运行的结果描述为“性能已经提升”。先验证可训练性和合法性，再在冻结 validation 上比较，最后才决定是否使用一次性 test。

## 10. 向组员介绍时的三分钟版本

> 我们的优化不是把 HPC 节点照搬进赛题，而是在赛题规定的端、边、云三层中增加多个异构实例。任务从只有 workload 扩展为核数、内存、GPU、能力标签和数据依赖，资源也具有对应容量；不兼容的任务—资源组合会在环境中直接 mask。原模型只对任务 DAG 做图编码，新模型另外构造资源图，用带宽和时延描述资源关系，再为当前合法的任务—资源对打分。完整调度仍由环境逐步插入时间线，不是 GNN 一次生成任务队列。训练使用 Actor、Critic、GAE 和 clipped PPO，评测继续以 HEFT 为统一参考。数据方面，STG v2 保留原约束，DAGBench补充大规模多领域 DAG，Topology Zoo用于测试网络拓扑泛化。旧模型和旧数据合同保留，用于兼容和消融。

## 11. 当前边界与下一步

- 当前 CPU 核数是可行性约束，不支持多任务按核数并行共享同一节点；
- 资源可用性、功耗、费用、动态到达和故障尚未进入主目标；
- 双图 PPO 目前提供完整可训练原型，但正式超参数、冻结 split 和多随机种子证据尚需按评测合同执行；
- Topology Zoo 的“网络节点→端/边/云计算节点”是人为投影，必须记录映射依据；
- 大到 1000+ 节点的 DAG 需要批处理、稀疏邻接矩阵或 PyTorch/PyG 版本，当前 NumPy 解析梯度实现更适合验证算法和合同正确性。
